# Phase 8.1 — Reliability and Citation Policy

## Problem discovered in Phase 8
The six-case synthetic evaluation produced five generated responses. The baseline included two invalid source IDs in the medication/note hybrid case: a placeholder SQL marker and a shortened document marker. Other inaccuracies in note interpretation were also observed.

## Objectives
1. Only show markers explicitly returned by patient-scoped SQL or ChromaDB retrieval.
2. Distinguish structured medication requests from narrative medication statements.
3. Retry generation once if the exact citation-marker audit fails.
4. If still invalid, suppress the generated answer and show a deterministic **evidence-only** listing, clearly marked as a fallback.
5. Preserve the baseline experiment for reproducibility; run the same six questions separately.

## Technical approach
- An application-controlled, read-only retrieval layer (`hybrid_assistant.retrieve_hybrid`) remains responsible for patient selection and evidence gathering.
- `reliable_assistant.generate_reliable_answer` sends selected patient evidence and an allowlist of source IDs to the local Qwen model.
- Every bracketed `[SQL:...]` and `[DOC:...]` citation in the generated answer must exactly match an allowlisted ID.
- The audit also checks for incomplete source markers and requires at least one citation from each evidence modality when that modality had retrieved records.
- At most one retry is enabled by default; an invalid final model answer is never displayed.
- A deterministic fallback prints selected SQL records with provenance and document metadata, not medical interpretations of the source texts.

## Known limits
- **Exact-ID checks are NOT claim-level source attribution.** A valid source identifier may still be attached to a false or unsupported claim.
- A free-form clinical statement may contain uncited sentences even if some valid markers are present. A stronger per-sentence claim validator is a future task.
- The system cannot verify medical plausibility, the patient's real-world clinical state, or the accuracy of Synthea-generated notes.
- An absent medication row may mean no eligible row was retrieved within the selected scope. It is not proof that a medication was never taken or prescribed.
- Patient-scoped data retrieval does not replace user authentication and authorization for a real clinical deployment.
- If a fallback is used, it must be counted separately from accepted model responses in the performance report.
- Repeated calls to Ollama may increase latency versus Phase 8.

## Reporting and comparison
The evaluation script uses the six `CASES` already defined in `evaluate_hybrid.py` with matching SQL and RAG retrieval settings. It writes new files only to the requested output folder.

`comparison_to_baseline.json` compares literal unknown citations for question-matched cases. It does not assert improvements in factual accuracy. The `manual_review.csv` for the new run must be scored independently before any comparison of human-reviewed quality.

## Out-of-scope
- Re-training or fine-tuning Qwen
- Medical diagnosis, clinical use, risk prediction
- Arbitrary SQL generated by the LLM
- Updates to Bronze, Silver, Gold, ChromaDB, Kafka, Spark, Azure/AWS or Power BI
